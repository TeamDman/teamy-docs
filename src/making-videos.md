# Make videos with code

Revisit these references when reusable video layouts, explanatory motion graphics or precise mathematical animation become useful. They are external options, not adopted Teamy dependencies. Initial references were reviewed on 7 October 2026; later additions are dated below. The renderer surveys did not test local rendering or integration. The separate delivery observations below concern an existing cloud-produced video.

## View and deliver a cloud render

**Observed, 2026-10-23:** a task-local file link in the producing chat opened and played a rendered video through the app; playback was user-verified. That is distinct from uploading the file into persistent Library storage. A Library upload failure neither establishes a render failure nor proves that task-file viewing is broken. Diagnose generation, playback and transfer separately.

App surfaces vary. A link handled by the owning task is not a promise that a raw workspace URL works in another chat, in an external browser or as an operating-system-local path. For Teamy iteration, prefer returning to the producing chat and its file link. Library remains an optional retention or delivery channel, rather than a mandatory upload for every revision. Preserve valuable final output independently; do not promise either channel retains it forever. Keep private Library download URLs out of public documentation and logs intended for publication.

**Observed transfer limitations, 2026-10-23:** an executor-side HTTP helper encountered a network failure. A native, host-mediated Library upload uses a different path; the helper's result did not establish that host upload would fail. A Windows helper also encountered an `os.setxattr` incompatibility. These are specific helper/runtime observations, not a general statement that rendering, Windows file access or Library is unavailable.

**Working decision:** do not build Teamy's artifact workflow around Python Library helpers or a WSL workaround for those helpers. Use the producing-chat link for current iteration, and evaluate the [proposed Rust-native transfer path](moving-files.md#proposed-cloud-to-desktop-transfer) when an owned desktop copy is needed. No native transfer implementation is claimed here. [Cloud-environment lifecycle](cloud-environments.md) explains why a local render and local commit are separate retention concerns.

Manim Community and `3b1b/manim` have diverged APIs, packages and ecosystems. Community examples use `manim`; ManimGL uses `manimgl` and `manimlib`. Follow the selected project's documentation and examples rather than mixing installation or API instructions. Review licenses for both the tool and any fonts, footage, audio or other assets used in a video.

ManimGX was inspected on 11 October 2026 at [commit `7ea9ad5fdd73ac2aa90a10549da15be94b6d0800`](https://github.com/academa-labs/manimgx/blob/7ea9ad5fdd73ac2aa90a10549da15be94b6d0800/README.md). Its [Python package](https://github.com/academa-labs/manimgx/blob/7ea9ad5fdd73ac2aa90a10549da15be94b6d0800/pyproject.toml) requires Python 3.13+, and its [Rust engine](https://github.com/academa-labs/manimgx/blob/7ea9ad5fdd73ac2aa90a10549da15be94b6d0800/rust/engine/Cargo.toml) uses PyO3 bindings and wgpu. The [migration guide](https://github.com/academa-labs/manimgx/blob/7ea9ad5fdd73ac2aa90a10549da15be94b6d0800/docs/content/user-guide/coming-from-manim-ce.md) targets CE's authoring API, not identical behavior or ManimGL compatibility: CE module imports and quality flags differ, timing and updater semantics differ, and LaTeX packages and `\def` do not convert through its Typst typesetting path. Check existing scenes individually before adopting it. The [changelog](https://github.com/academa-labs/manimgx/blob/7ea9ad5fdd73ac2aa90a10549da15be94b6d0800/docs/content/changelog.md) records 0.1.0 and 0.1.1; this is an early release, and the README's speed comparisons are upstream measurements on specific scenes and hardware, not locally verified results. ManimGX's own [source license](https://github.com/academa-labs/manimgx/blob/7ea9ad5fdd73ac2aa90a10549da15be94b6d0800/LICENSE) is MIT, but its [README license section](https://github.com/academa-labs/manimgx/blob/7ea9ad5fdd73ac2aa90a10549da15be94b6d0800/README.md#license) says native wheels include x264 and are GPL-3.0-or-later as a whole; review the bundled-component notices before redistribution.

## Psychopomp

[Psychopomp](https://github.com/kitlangton/psychopomp) was reviewed on 18 October 2026 at [commit `3a50a2b`](https://github.com/kitlangton/psychopomp/blob/3a50a2bf1897ddeaa4e5a71df85224107aaf734b/README.md). It is a code-first motion-graphics reference: Rust scene programs write JSON scene plans, then a wgpu renderer exports video through FFmpeg or plays a native interactive presentation. Its examples include animated code diffs, diagrams and charts; the [renderer manifest](https://github.com/kitlangton/psychopomp/blob/3a50a2bf1897ddeaa4e5a71df85224107aaf734b/crates/psychopomp-render/Cargo.toml) supplies implementation evidence.

The README calls it an early prototype tested on macOS with Metal. Rendering requires a recent Rust toolchain, a GPU and FFmpeg with `libx264`; Windows and Linux readiness was not established by this review. Project code is MIT licensed, with separate bundled font and icon notices. Status: surveyed source reference, with no installation, rendering or presentation tests here and no dependency adoption or TeamyStyle requirement.

### PDoomVideo strategy

Source inspected at [commit `fa546a3`](https://github.com/JohnHeibel/PDoomVideo/tree/fa546a38092e75f2b079e6a86d6abc54dd525d17). The [package manifest](https://github.com/JohnHeibel/PDoomVideo/blob/fa546a38092e75f2b079e6a86d6abc54dd525d17/package.json) declares p5 `^2.3.3`, p5.brush `^2.2.3` and puppeteer-core `^25.11.0`; these are dependency ranges, not a claim that arbitrary future versions work. The [studio](https://github.com/JohnHeibel/PDoomVideo/blob/fa546a38092e75f2b079e6a86d6abc54dd525d17/studio.html) assembles shared drawing helpers and chapter scripts into a 1920×1080 canvas and fetches fonts externally.

The [renderer](https://github.com/JohnHeibel/PDoomVideo/blob/fa546a38092e75f2b079e6a86d6abc54dd525d17/render.mjs) calls `renderAt(t)` for selected timestamps. It can produce contact sheets, stills, short clips and parallel, resumable JPEG frame batches, then encode those frames with the bundled song through FFmpeg (H.264/yuv420p plus AAC). Timestamp addressing is useful for reproducible authoring, but cross-platform pixel determinism was not established. The resume check uses file presence and size, so production adaptation needs content/version invalidation rather than assuming old frames match a changed scene.

This is a project-specific pipeline: duration and audio path are fixed, Chrome defaults to a Windows installation and launch flags select D3D11. Linux browser/GPU flags, local licensed fonts, independently supplied audio, frame storage, render memory, cancellation and failure checks need qualification. No resource benchmark or Linux test was performed. Start with a short synthetic scene and a small worker count before scaling. Preserve editable sources only when requested in extras; every successful storytelling delivery still needs the required playable video.
