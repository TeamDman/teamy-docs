# Coordinate through shared state and messages

Choose what is shared, who may observe it, who may change it, and what happens when a participant disconnects. A shared task record can help a worker find pending work, but the record is not permission to act. Link any proposed action to its scope and authority as described in [delegated authority](delegated-authority.md).

## Shared traces and state

*Stigmergy* describes indirect coordination: an action leaves a trace in an environment that can stimulate another action. A task marked ready, then observed by another worker, is a possible software example. Artifacts and receipts need provenance, freshness, deduplication and conflict rules; the trace grants no authority. This is a coordination lens, not an authorization protocol or a guarantee of correct convergence. The [Heylighen paper](https://researchportal.vub.be/en/publications/stigmergy-as-a-universal-coordination-mechanism-i-definition-and-/) is conceptual research prior art.

[Spacetime](https://spacetimedb.com/) (formerly SpacetimeDB; documentation and package names still use that name) is a candidate for applications with transactional server logic and live subscriptions. Its [chat tutorial](https://spacetimedb.com/docs/tutorials/chat-app/) starts a local host with `spacetime start`, publishes a module, and connects clients. Distinguish a server-side module SDK, a client SDK, a managed child server process and an engine embedded in the application process. Logic running inside the database is not itself engine embedding. The inspected [standalone library source](https://github.com/clockworklabs/SpacetimeDB/blob/3e67feadab6b344746b2775f62257259d27a7b25/crates/standalone/src/lib.rs) exposes internal initialization, but that alone does not establish a supported, stable drop-in embedding API. Its [portable datastore](https://github.com/clockworklabs/SpacetimeDB/blob/3e67feadab6b344746b2775f62257259d27a7b25/crates/portable-datastore/src/lib.rs) supports in-memory module unit tests; this does not establish a durable embedded production server. Investigate lifecycle, API support and licensing before designing around it. The [FAQ](https://spacetimedb.com/docs/intro/faq/) describes source-available BSL-1.1 terms and later conversion; review the actual terms for the chosen version. No Spacetime service was run or adopted here. Authentication and authorization still belong to the application: the [auth-claims guide](https://spacetimedb.com/docs/core-concepts/authentication/usage) describes checking callers and issuers.

Locally inspected Poche-3 documentation describes native Veilid as its default; Poche-4 describes Bevy and SpacetimeDB. These are checkout labels, not separate public repositories. Poche's [Spacetime branch at `e5e767c`](https://github.com/TeamDman/Poche/blob/e5e767cc6b545b725994e50984d01d69091bface/README.md) is the related product-path reference; its [desktop workflow](https://github.com/TeamDman/Poche/blob/e5e767cc6b545b725994e50984d01d69091bface/docs/spacetimedb-desktop.md) starts a separate server and publishes a module. The separate model-checking branch describes experimental Veilid and replicated-log work: its [application identity](https://github.com/TeamDman/Poche/blob/model-checking/docs/application-identity.md) separates principals and recipients from routes, and its [viewer projections](https://github.com/TeamDman/Poche/blob/model-checking/docs/viewer-projections.md) describe grants scoped to a player, recipient and epoch. Revocation governs future projections; it cannot retract data already disclosed. These are documented designs and branch-specific prior art, not new tests.

## Transport is a separate decision

[Veilid](https://veilid.com/) is a candidate peer-to-peer application framework with a core library for applications. Its [messaging documentation](https://veilid.gitlab.io/developer-book/apps/api/appmessaging.html) distinguishes a call expecting a response from a one-way message; [routing contexts](https://veilid.gitlab.io/developer-book/apps/api/routing_contexts.html) distinguish direct and safety routing. Attaching a node does not itself anonymize both endpoints, and Veilid is not automatically a VPN supplying general IP reachability. Evaluate identity binding, routing, disconnection, message size and actual privacy properties for a particular version and threat model. A route or encrypted channel alone does not authorize a requested action or guarantee delivery. No Veilid application was tested here.

Teamy Torrent's inspected documentation describes metainfo and piece verification plus restricted loopback experiments, not qualified public torrent traffic. Teamy VPN's inspected documentation describes separately scoped WireGuard experiments and an external-client contract, not qualified production isolation. A torrent client's intended VPN binding requires enforcement and leak tests, not just selecting a VPN in its UI. For existing mesh and tunnel comparisons, see [networking](networking-survey.md).

For studying a Rust BitTorrent implementation, Jon Gjengset's [first implementation stream](https://www.youtube.com/watch?v=jf_ddGnum_4), [follow-up](https://www.youtube.com/watch?v=r0srf3kfZbs) and [source repository](https://github.com/jonhoo/codecrafters-bittorrent-rust) are educational prior art, not evidence that Teamy Torrent implements the whole protocol or is ready for public traffic.

## Synchronized viewing and chat

[Syncplay](https://syncplay.pl/) coordinates playback in rooms through a server; it is not a file-sharing service. [mpv](https://mpv.io/) is a media player with both a CLI and an embeddable C API. Syncplay's [client guide](https://syncplay.pl/guide/client/) documents mpv chat and player integration. Compatibility is useful because these tools are already used in the Teamy ecosystem. A compatible client or bot that exchanges messages in chat is a proposal, not an existing feature.

Treat chat as untrusted input, not an authenticated command or an instruction to an agent. A future bot needs a bounded typed grammar, authenticated identity, issuer/room/recipient/expiry binding, replay and duplicate protection, and explicit authorization for each effect. Room membership or a display name alone is not proof of authorization. Pin and test the server and configuration and require validated secure transport for authority-bearing extensions; Syncplay's [server guide](https://syncplay.pl/guide/server/) documents optional TLS. Do not place credentials or private data into shared chat. Media URLs and filenames can reveal information or trigger external requests; Syncplay's client guide describes trusted-domain settings.

mpv's [JSON IPC](https://mpv.io/manual/stable/#json-ipc) lacks authentication and encryption and exposes commands capable of executing programs. Never forward chat or network payloads into raw mpv commands. A proposed local mediator must enforce socket or named-pipe permissions and allowlist specific playback operations and media identity. [libmpv](https://mpv.io/manual/stable/#embedding-into-other-programs-libmpv) offers a C embedding API; it still requires its caller to enforce authorization.

[Teamy Terminal at `70d5706`](https://github.com/TeamDman/teamy-terminal/blob/70d57067e99bea9a1143cafa9e55ffa33d8afc7c/README.md) is an implementation reference for a terminal core and PTY presentation. Displaying a message in a terminal does not make it a trusted request or grant authority to execute it; terminal control sequences also require careful handling. This does not claim a Syncplay integration.

[Vetchricore](https://github.com/TeamDman/Vetchricore) is a learning prototype for Veilid terminal chat and mpv/VLC discovery and configuration. The inspected material does not establish playback synchronization or application-authenticated payload senders; it is not a secure delegated-action channel.

## A minimal coordination slice

Use an in-memory synthetic task board first: one writer marks a test task ready, a reader observes it, and a separate authorized action changes it to done. Check duplicate and replayed events, an unauthorized writer, stale observations and a restart. No network or real files are needed. A separate proposed Syncplay compatibility slice can parse and display bounded synthetic messages read-only before any control action is considered. Only after data and authority boundaries are clear, compare an actual transport or shared-state backend under the same cases; a successful local test does not establish distributed reliability.
