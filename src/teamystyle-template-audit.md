## Read each decision with its enforcement scope

“Observed” reports implementation, not a new policy. “Required” refers to TeamyStyle or an existing template instruction. “Gap” means the stated norm needs further enforcement or qualification. A test's presence is separate from a passing run.

## What the serde policy actually catches

The user-required norm is Facet instead of serde for new first-party Rust integration. The inspected configuration has three mechanisms with different coverage:

1. `disallowed_methods = "deny"` enables the `clippy.toml` entries for `serde_json::{from_str,from_slice,to_string,to_string_pretty,to_writer,to_writer_pretty}`. Their reasons point to `facet_json` equivalents, including `to_writer_std` and `to_writer_std_pretty`. This list does not include every serde API or every JSON library.
2. `disallowed_macros = "deny"` enables the `serde_json::json!` restriction, in addition to print macros and `std::ptr::addr_of_mut!`. The latter recommends Rust raw reference syntax. This is configured API enforcement, not a blanket ban on pointer manipulation.
3. `clippy.toml` lists `serde::Serialize` and `serde::Deserialize` under `disallowed-types`. Although Cargo does not explicitly set `disallowed_types`, the installed Clippy describes this lint as warn-by-default, so the gate's `-D warnings` makes detected violations errors. The local fixture below confirms direct and renamed trait-use rejection. It does **not** reject derive-only use on the tested toolchain.

An isolated offline fixture on 15 October 2026 used the template's actual `clippy.toml`, deny-level method/macro settings and `-D warnings`, with Clippy `0.1.96 (ac68faa20c 2026-05-25)`, serde 1.0.229 and serde_json 1.0.151. Direct `serde::Serialize`, aliased Serialize/Deserialize bounds, `serde_json::to_string` and `serde_json::json!` produced the intended `clippy::disallowed_types`, `disallowed_methods` and `disallowed_macros` errors (exit 101). A struct with only `#[derive(serde::Serialize, serde::Deserialize)]` and no explicit trait use passed (exit 0). Both binary and test targets were checked with `--all-targets --no-deps`. The fixture verified the observed serde-related restrictions, not every lint or every target kind; it did not run the template's full gate.

The required follow-up for a project claiming full first-party enforcement is to cover that derive-only hole and qualify negative fixtures for direct, qualified and renamed method/macro/trait uses, derives, tests/examples/build targets, plus positive Facet fixtures. This inventory records that work as an **enforcement gap**, not a completed template change. Adding an explicit direct dependency named serde also needs manifest/metadata policy: API lints alone can pass when the dependency is unused, renamed or used through an unlisted API.

Inspect `cargo metadata` and `cargo tree` for the resolved graph and dependency reasons. `tracing-subscriber`'s JSON support may bring serde-related crates transitively; `--no-deps` does not lint them. A direct-API ban, a direct-dependency audit, a full transitive policy, and a security/license advisory audit are four different claims. No template `deny.toml` or equivalent graph/advisory audit was found in this inventory. Minimize and justify dependencies without calling this an implemented transitive serde ban.

## Keep enforcement and acceptance together

An exact compiler diagnostic is useful evidence. A negative fixture should fail for the intended lint, rather than an unrelated unresolved import; a positive fixture should exercise the supported replacement. The current print policy runner checks diagnostic codes, isolates scratch output and records each case. Extend that approach for new policy gates rather than adding a text search and calling it compiler enforcement.

Run the adopting project's gate against the actual manifest/configuration and preserve the resulting scope and limitations. Changes to logging, parsing, cancellation, generation or platform code need their own behavioral evidence. Publishing this inventory does not publish the newer template source or establish that existing installed binaries satisfy every rule.
