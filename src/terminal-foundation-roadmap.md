# Terminal and Windows foundation roadmap

This is a shared backlog and ownership map, not a statement that these features already ship. Ordering is flexible: a consumer can prove a capability first, then a reviewed implementation can move to the reusable template. Keep GUI work secondary to a usable terminal foundation. Do not install a service, change security configuration or perform recovery as part of a documentation or synthetic test.

| Work | Owner and current status | Evidence and next qualification |
| --- | --- | --- |
| Typed, bounded OTLP log ingestion | `teamy-tracing`: implemented and synthetic-tested in local commits `9fb1cd3` and `207658c` on the implementation branch. The receiver explicitly binds IPv4 loopback, with bounded bodies and store, and is not a durable queue. | [Telemetry contracts](logging.md#preserve-field-types-before-crossing-ipc); real Codex export remains unqualified. Never send an ingested event back to its own OTLP exporter. |
| Inline counters with logs in scrollback | Teamy Codex: implemented locally with a synthetic loopback test and a PTY smoke; the template does not yet provide this. The command prints bounded event summaries and process logs above an inline counter view. | [Inline logging and terminal ownership](terminal-ownership.md#put-logs-above-an-inline-view). The synthetic tests cover insertion, loss, truncation and writer failures; terminal hosts, resize and restoration failure handling need broader qualification before promotion. |
| Reusable console/file and terminal-owner integration | `teamy-tracing` and `teamy-rust-cli`: proposed. Callers own sinks, filtering and lifecycle; preserve batch stdout and file logging while a TUI owns the terminal. | Cloud-Terrastodon's bounded capture, acknowledged replay and terminal coordinator are prior art. `teamy-tracing`'s existing formatter is not an external-record sink. |
| Tray and app-console visibility | Both Teamy Codex and the planned Teamy Defibrillator need tray control; `teamy-rust-cli` should expose optional Windows foundation capabilities. Not implemented here. | [Piing and tb](system-tray.md). Track owned, inherited and ConPTY console contexts; do not hide a shared parent terminal. Restore resources and screen state on exit. |
| Screen-state stack and global input capture | Optional `teamy-rust-cli` foundation, then consumers. Design stage. | For Windows, evaluate [Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input) with `RIDEV_INPUTSINK` for both capture and runtime matching. [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey) registers a known chord; it does not capture an arbitrary sequence. Preserve the previous binding during capture, disarm actions, preview keys, wait for release before rearming, and avoid logging unrelated keystrokes. Escape ends capture; provide separate cancel and clear actions. Suppression, if needed, requires a separate hook and latency review. |
| Elevation and service lifecycle | Optional, removable Windows APIs in the template; planned Defibrillator consumer. Design stage only. | [Teamy MFT's daemon and elevation](logging.md#learn-from-piing-and-mft) are prior art. Defining an API does not install, start or elevate a service. Review caller identity, ACLs, fixed operations, cleanup and tests before use. |
| Defibrillator recovery | Separate local application: dry-run fake recovery, input capture/matcher, visibility transitions, an inline Ratatui status view and validated binding persistence implemented through local commit `d5c4b86`; sixteen tests passed. No published repository, live Windows adapter, DWM recovery or elevated service is established. | A future DWM recovery service must identify the authorized caller's session itself, expose a fixed operation rather than client-selected paths or PIDs, reject remote clients, validate handles, and enforce cooldown and one in-flight operation. Five seconds is an observation timeout, not proof of recovery or permission to start a replacement process. No privileged tests are authorized here. |
| GUI telemetry explorer | Later Teamy Codex enhancement. The generic synthetic egui example is implemented; a Codex application and real capture are not. | [egui and eframe](egui-eframe.md). The terminal receiver and safe logging boundary come first. |

Keep the feature flags and `cfg(windows)` boundary explicit: a new project can omit Windows-specific tray, console, input, elevation and service dependencies. Promotion to the template requires tests for cleanup and failures, an updated reference implementation and consumer adoption; adding a row here alone changes no template or application behavior.
