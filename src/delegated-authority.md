# Delegate only the authority an action needs

A planner may know that an operation accepts a type and produces another. That is useful for finding candidates; it does not grant permission to perform the operation. Describe the principal, resource, permitted operations, scope, lifetime and delegation rules separately from the operation's input and output types. An effect annotation is a claim to audit, not enforcement. See [typed capability planning](decision-planning.md).

## References as authority

In an object-capability model, a reference both designates an object and conveys the authority to invoke its exposed interface. A party can delegate an authority it holds; giving a worker a narrower wrapper can limit the operations that worker can request. The wrapper and every other path to the underlying authority must actually enforce that restriction. An identifier, a serializable Rust type or a filtered response alone is not an unforgeable capability.

[Cap'n Proto RPC](https://capnproto.org/rpc.html) is a research candidate for capability-carrying interfaces and promise pipelining. Its documentation distinguishes protocol features by implementation level and states that the RPC protocol does not specify encryption. Verify the implementation's supported levels, authenticated transport, lifetime, disconnection and revocation behavior before adoption; serialization alone does not supply the RPC authority model. No integration is claimed here.

[E's Grant Matcher puzzle](http://www.erights.org/elib/equality/grant-matcher/index.html) is conceptual prior art for least authority, delegation and reference identity. Two donors want their contributions combined only if they designate the same recipient. A deceptive forwarder can pass behavioral checks and then intercept the donation, so consequential transfers need appropriate reference identity and intended authority. This is a thought experiment, not a ready-made implementation or proof that two named resources are identical. The live site timed out during this review; the author's [source at `1e0bd13`](https://github.com/erights/erights-org-website/blob/1e0bd13a92650638077aa95b920e0647d7f12b3b/elib/equality/grant-matcher/index.html) is also available. E's [delegation discussion](https://www.erights.org/elib/capability/conspire.html) explains a further limit: a cooperating holder can proxy its authority to someone else.

[Teamy's Policy-Based Access Control paper](https://github.com/TeamDman/TPBAC/blob/main/paper/main.typ) is an unfinished policy proposal, not executable enforcement. It describes default denial, at least one matching allow with no matching deny, immutable action attempts and audit-only rules. Compare those semantics with an actual enforcement point and its delegation behavior before adoption.

## Scope cloud permissions at the enforcing service

Azure role assignments combine a principal, role and [scope](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview); permissions can be inherited down the resource hierarchy. Choose the narrowest workable scope and review inherited grants as well as the new assignment. [Role definitions](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-definitions) distinguish control-plane Actions and data-plane DataActions. `NotActions` is not a deny: another assignment may grant the operation. [Role assignment conditions](https://learn.microsoft.com/en-us/azure/role-based-access-control/conditions-overview) add attribute checks only where the relevant service and operations support them. Consult that service's documented conditions and authorization model; do not assume arbitrary response fields can be individually protected by general Azure RBAC.

For example, returning only resource names from a broker reduces what that response exposes. If the broker retains a credential that can read all properties, the upstream authority has not been revoked. The broker is an additional enforcement boundary and must guard all access paths, credentials, logs and errors. Distinguish resource scope, permitted action, response projection and endpoint-specific secret operations; consider alternate paths, caches and revocation. Validate both an allowed and a denied operation with the actual principal, scope and service; an empty filtered result is not a denial test.

Network policy is another boundary. [Tailscale app capabilities](https://tailscale.com/docs/features/access-control/grants/grants-app-capabilities) can convey capability data to a receiving application, which must interpret and enforce its schema. If using Serve-provided headers, prevent clients from bypassing or spoofing the trusted proxy path. [WireGuard](https://www.wireguard.com/) and network reachability do not by themselves authorize a particular file or application action.

Operating systems enforce different boundaries. [Windows access control](https://learn.microsoft.com/en-us/windows/security/identity-protection/access-control/access-control) uses principals, resource rights and ACLs, including inheritance. [Linux capabilities](https://man7.org/linux/man-pages/man7/capabilities.7.html) divide privileged operations into per-thread units; they are not the same concept as object-reference capabilities. SSH keys authenticate access, but effective account and process authority still matters. OpenSSH supports [authorized-key restrictions](https://man.openbsd.org/sshd.8#AUTHORIZED_KEYS_FILE_FORMAT), including forced commands and `restrict`; a successful SSH login alone does not limit a session to a particular application operation.

## A small test before integration

Model a synthetic read-only worker and a separate write operation. Give the worker only a narrow test handle; show that it can read the intended record but cannot obtain the underlying full handle or perform the write. Test an expired or revoked grant, a forged identifier, duplicate requests and a request from the wrong identity. Record the difference between policy decisions, a handle's actual enforcement and a transport failure. This is proposed validation, not an implemented capability system.
